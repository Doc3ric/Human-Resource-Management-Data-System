MODULE 12 — DYNAMIC STATISTICAL SCOREBOARD (SYSTEM-WIDE, EQUITABLE, NON-REDUNDANT)
A single, consistent, living statistical layer across the ENTIRE system — every module and sub-module — built from one shared, reusable scoreboard component. The design is equitable (each module gets the depth of statistics it actually warrants — no more, no less), non-redundant (each metric has exactly one canonical home; the same number is never counted/displayed in two places), and built to be friendly, informative, and visually alive. CORE CONSTRAINT (unchanged): every scoreboard respects its host module's privacy, RBAC, confidentiality, and is_renewed gating — aggregate only; never SPI, never RACCS/confidential content, never pre-comparison deliberation scores, never incident names/narrative.
12.1 ONE SHARED COMPONENT: build a single reusable scoreboard widget used everywhere — KPI stat tiles (large number, label, trend arrow, sparkline), charts (bar/line/donut/progress via the existing library), a filter bar matching the host module's filters, live auto-refresh (10–15s polling or existing real-time channel; manual refresh + "last updated" stamp), and export (CSV/PDF, standard header/footer + citations, logged). Themed entirely via theme.css semantic variables. Every scoreboard in the system is an instance of THIS component — never bespoke one-offs — so look, behavior, and accessibility are uniform.
12.2 EQUITABLE ALLOCATION (right-sized per module, not uniform): scale the scoreboard to each module's actual decision value. Three tiers: (a) FULL scoreboard (KPI row + 2–4 charts + trends) for analytics-heavy modules — GAD/Workforce, Leave Violations, Incidents, Renewal, IDCC/Records, Executive Dashboard; (b) COMPACT scoreboard (a slim KPI strip, 2–4 tiles, optional one mini-chart) for operational modules where stats inform but aren't the point — Recruitment view, Plantilla, LGU service requests, Photo/intake; (c) INLINE metric (a single contextual figure or progress indicator, no full board) for narrow sub-modules — e.g., a vacancy's applicant-count badge, a member's completion fraction. A module gets a FULL board only if it has decisions that statistics meaningfully drive; otherwise compact or inline. This prevents dashboard bloat and keeps each view purposeful.
12.3 NON-REDUNDANCY — CANONICAL OWNERSHIP OF EACH METRIC: every statistic has ONE canonical home module that owns and displays it in full; other modules that need the same figure show it only as a lightweight contextual reference (a single tile or a linked figure), never a re-computed duplicate board. Establish a shared metrics service so all surfaces read the same computed value from one source (no parallel counts that can disagree). Canonical owners (examples): active/not-renewed headcount → Renewal (1A); workforce demographics (sex/PWD/solo-parent/age/SG) → GAD/Workforce; leave-violation counts/funnel → Leave Violations (2B); incident counts/tracks → Incidents (3A); deliberation completion → Monitoring Board (6A); document/retention stats → IDCC/Records; sensitive-bit holders → RBAC (4A, Admin). If module B needs module A's number, it shows a small "reference tile" that links to A's full board — it does not rebuild the chart. The Executive Dashboard is the ONLY place that aggregates across owners, and it pulls each headline figure from its canonical owner (one source of truth), presenting a curated cross-system summary rather than re-counting.
12.4 FRIENDLY, INFORMATIVE, APPEALING, ACTIVE (the display standard for every instance):
- Clarity first: each tile states what the number means in plain language and its timeframe; avoid jargon; every chart has a one-line plain-language takeaway (auto-generated insight caption) so a non-analyst instantly understands "what this is telling me."
- Active/alive: smooth count-up animation on load, live updating values, animated trend arrows (up/down/flat) with color from semantic theme variables, sparklines showing recent movement, and subtle transitions on refresh (never jarring). A gentle "updated just now" pulse on the last-updated stamp.
- Informative depth on demand: tiles are calm by default but expandable — click/tap to reveal the breakdown, the trend over periods, and the contributing factors (progressive disclosure keeps the surface uncluttered while depth is one tap away).
- Appealing & purposeful: generous whitespace, clear visual hierarchy (one hero metric per board, supporting metrics secondary), consistent iconography, semantic color used meaningfully (success/warning/danger conveys state, not decoration), and empty/zero states that are encouraging and clear ("No violations this period — all clear") rather than blank.
- Actionable: where a statistic implies an action, surface a contextual link ("3 notices pending → review") so the board drives work, not just observation — but only within the user's RBAC scope.
- Accessible & responsive: WCAG 2.1 AA contrast (theme themes already validated), keyboard-navigable, screen-reader labels on every figure and chart, and graceful reflow — KPI tiles stack and charts simplify on mobile; never a cramped grid on small screens.
12.5 PRIVACY/RBAC/GATING (unchanged, applies to every instance): RBAC-scoped (counts reflect only permitted data; supervisors see only their unit); privacy-first (aggregate only — no SPI, no confidential/RACCS content, no pre-comparison deliberation scores, no incident names/narrative; escalated/grave and RACCS items appear only as anonymized counts); is_renewed-gated where the metric concerns active personnel; exports logged; tooltips carry the host module's legal citations. The privacy and aggregation rules are enforced IN the shared component, so no instance can bypass them.
12.6 INTELLIGENT, NOT NOISY: scoreboards surface what changed and what needs attention rather than dumping every possible count. Prioritize: deltas (what moved since last period), exceptions (what crosses a threshold), and readiness/completion (what is/ isn't done). Suppress static, low-value counts. The goal is a board a busy HRMO chief can read in ten seconds and know what needs action — informative density without clutter.

12.7 EXISTING-DISPLAY AUDIT & CONSOLIDATION (Phase A/B/C, before any build): conforming to this module means rationalizing displays that already exist — not a blind sweep. During the discovery protocol the developer MUST: (a) Phase A — inventory EVERY existing statistical display, KPI tile, chart, and count across the current system, recording for each its location, the metric(s) shown, and how each is computed; (b) Phase B — identify redundancy (the same figure displayed or re-counted in more than one place) and map each metric to its single proposed canonical owner per 12.3 and the registry in 12.8; (c) Phase C — document a written DE-DUPLICATION / CONSOLIDATION MAP: for each duplicated metric, the proposed canonical owner, which displays collapse into reference tiles, which boards downgrade from FULL to COMPACT or INLINE per 12.2, and which bespoke displays are replaced by the shared component; then proceed directly into executing the consolidation, preserving every working feature. Treat existing boards as something to audit and rationalize, never to ignore or silently delete.
