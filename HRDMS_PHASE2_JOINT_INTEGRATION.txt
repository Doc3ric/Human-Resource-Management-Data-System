PARALLEL-BUILD COORDINATION PROTOCOL (read before assigning work to two coders)

══════════════════════════════════════════════════════════════════════


This specification is split into a SHARED FOUNDATION (build first, single-threaded) and TWO INDEPENDENT TRACKS that may then be assigned to two different coders (e.g., one to Claude, one to Gemini) and built AT THE SAME TIME without either one's work touching a file, table, blueprint, or page the other is also editing.

WHY A SHARED FOUNDATION COMES FIRST: the master schema, the RBAC permission matrix, the core document pipeline (IDCC), and the shared statistical-scoreboard component are read or extended by nearly every feature module in both tracks. If two coders each tried to create these independently and in parallel, their schemas/matrices/components would conflict when merged. Building these once, upfront, removes that conflict entirely — after Phase 0 is complete and merged, the two tracks below share NOTHING they both write to.

TRACK BOUNDARIES: Track A owns the personnel lifecycle, leave, records-compliance, and incident/training domain. Track B owns the recruitment deliberation, document-capture, and citizen/appointment-facing domain. Each track's modules read from the shared Phase 0 foundation (schema, RBAC matrix, IDCC core, scoreboard component) but never modify Phase 0 files, and never touch the other track's tables, blueprints, or frontend pages. See the FILE/TABLE/BLUEPRINT OWNERSHIP MATRIX at the end of this document for the concrete boundary.

HOW TO ASSIGN: give Coder 1 the "PHASE 0" section (or have it built by whichever coder starts first, then have both coders review/pull it before diverging) plus the entire "TRACK A" section. Give Coder 2 the same Phase 0 section plus the entire "TRACK B" section. Each track section below is fully self-contained — it restates every functional requirement, build note, and RBAC/citation detail needed for that track's modules, so neither coder needs to open the other track's section to understand or build their own.

SYNC POINTS (the only two moments the coders' work must be reconciled): (1) after Phase 0, both coders should confirm they are building against the identical schema/RBAC-matrix/IDCC-core/scoreboard-component before diverging into their tracks; (2) after both tracks are functionally complete, a short "PHASE 2 — JOINT INTEGRATION" pass (below) builds the Executive Dashboard (which pulls headline figures from BOTH tracks' canonical metric owners) and runs the cross-track validation payloads — this is the only place the two tracks' output is combined.



EXAMINE-BEFORE-BUILD DIRECTIVE (applies to every module in both tracks below): Some of these functional requirements may already exist, in whole or in part, in the current HRDMS codebase (confirmed during Phase A discovery). Where that is the case, the assigned coder must NOT rebuild from scratch. Instead: (1) examine the existing implementation — its data model, logic, and UI; (2) audit it against this module's specification to identify gaps, inefficiencies, or rigid/hardcoded behavior; (3) improve or redesign it to be more dynamic, efficient, and maintainable (e.g., data-driven instead of hardcoded, reusable components instead of one-off code, single-sourced instead of duplicated), while preserving every currently working feature; and (4) confirm the redesign still serves the system's overall intent — a single coherent HRDMS, not a patchwork of inconsistent implementations. This applies whether the coder is starting a module fresh or improving prior work, and applies equally to both coders on both tracks.
