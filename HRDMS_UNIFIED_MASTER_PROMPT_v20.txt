MODULE 1A — SYNCHRONIZED RENEWAL STATUS & SIGNAL ARCHITECTURE
Additive to Module 1. Solves cross-module renewal drift for casual and JO/contractual personnel. PRINCIPLE: detection is distributed (any module may notice and flag a renewal signal); the source of truth is single (only an authoritative renewal act commits is_renewed). No module may infer renewal as a side effect of unrelated activity (submitting an IPCR target, editing a record, filing leave, appearing in payroll must NEVER silently set is_renewed=true).
1A.1 Single source of truth: is_renewed plus renewal effectivity dates are owned by the appointment/contract record in the Recruitment/Appointments module (M4), where the legal act lives. Every other module READS this; none writes it directly.
1A.2 Signal table (detection layer): create tbl_renewal_signal (signal_id PK; personnel_id FK→tbl_employee_master; rating_period; source_module ENUM('PERFORMANCE','RECORDS','LEAVE','RECRUITMENT','PAYROLL','OTHER'); signal_type VARCHAR e.g. IPCR_TARGET_SUBMITTED, RECORD_EDITED, CONTRACT_UPLOADED, LEAVE_FILED, PAYROLL_ACTIVE; signal_strength ENUM('AUTHORITATIVE','CORROBORATING','WEAK'); created_by FK→tbl_user; created_at TIMESTAMP; notes TEXT). When a module notices activity implying an employee is active, it INSERTS a signal row — it does not mutate is_renewed.
1A.3 Signal strength rules: AUTHORITATIVE = an actual signed appointment/contract with effectivity dates was recorded (in practice emitted only by M4 Appointments, or by Records when uploading the signed renewal contract through the IDCC pipeline as APPT-33A or the casual/JO contract type). AUTHORITATIVE alone may set is_renewed=true (via the commit service in 1A.6). CORROBORATING/WEAK = IPCR target submitted, record edited, leave filed, payroll presence — these accumulate as evidence and drive prompts ONLY; they never set the flag.
1A.4 Per-module behavior: Performance Management — checking that an employee submitted their IPCR target writes a CORROBORATING signal; if that employee is is_renewed=false, show inline: "This employee is not tagged as renewed for this period. IPCR submission recorded as a pending signal. Resolve renewal status before finalizing this rating cycle." It does NOT assume renewal. Records — editing a record writes nothing to renewal; only uploading the signed renewal/appointment document emits the AUTHORITATIVE signal. Leave/Payroll/others — CORROBORATING signals only. (JO/COS remain blocked from leave accrual per the cross-cutting guardrail regardless of signals.)
1A.5 Synchronized Renewal Status Widget: build ONE shared embeddable widget that every module renders off the same is_renewed value and the same tbl_renewal_signal rows, so the notification is inherently synchronized (one truth, no copies to drift). Wherever an employee with is_renewed=false appears (performance tracker, records view, batch renewal, personnel inventory), the widget shows a consistent badge, e.g.: "Not renewed for [rating_period] · [N] activity signals detected ([signal types]) · No authoritative renewal on file" using var(--color-warning-bg). Resolving status in one place updates it everywhere because there is only one source.
1A.6 Single commit path, many launch points: provide ONE shared batch-renewal commit service with all guardrails (JO/COS legality checks, mandatory effectivity-date capture, AUTHORITATIVE-signal-or-explicit-authority requirement, audit logging). Modules MAY expose their own launch buttons and filters in their own context (e.g., Performance Management "Process renewals for those who completed their rating cycle"; Records its own entry point), but ALL launch points call the SAME commit service — never their own write logic. What differs per module is the filter and framing; what stays identical is the commit path, the guardrails, and the audit trail. This prevents multiple code paths setting is_renewed under differing definitions (a COA-disallowance/data-drift risk).
1A.7 Commit authority (RBAC-governed): by default ONLY PHRMO / the Appointments Unit may execute the renewal commit. Authority is delegable solely through the Role-Permission matrix via a dedicated permission bit (e.g., renewal_commit). A module's launch button is visible/enabled only to sessions holding renewal_commit; all other roles may view status, add CORROBORATING signals, and request renewal, but cannot commit. Every commit and every delegation change is written to tbl_audit_log (who committed, for whom, rating period, effectivity dates, source signal).
1A.8 Request-to-renew flow (for non-authorized modules): a module without renewal_commit may raise a "Request Renewal" action that notifies PHRMO/Appointments and attaches the accumulated signals as supporting evidence; PHRMO then commits (or rejects with a logged reason). This lets originating offices surface real active-but-unpapered cases without granting them commit authority.
1A.9 Compliance: renewal of casual/JO personnel is a formal HR act tied to an actual appointment/contract with effectivity dates; the system must never represent inferred activity as a renewal. Tooltips cite 2025 ORAOHRA (appointment/renewal as a formal act) on the commit control and DOLE-CSC-COA-DBM JC No. 1 s.2017 on JO/COS rows.

MODULE 1B — EMPLOYEE LIFECYCLE EXCLUSION & RECORDS RETENTION MATRIX
Additive to Module 1/1A (active-status gating) and Module 2/Module 9 Stage 8 (NAP retention). Two linked capabilities: (A) extend the live-report exclusion beyond "not renewed" to ALL inactive lifecycle states (separated, retired, terminated, end-of-term, and unrenewed casual/JO/contractual), and (B) a portable, configurable Records Retention & Disposal Matrix in the Records module for easy online reference of each record series' lifecycle.
1B.1 Employee lifecycle status: every employee record carries a lifecycle_status (e.g., ACTIVE, RESIGNED, RETIRED, TERMINATED/DISMISSED, END_OF_TERM, TRANSFERRED, DECEASED, AWOL_DROPPED, NOT_RENEWED for casual/JO/contractual), an effective date of the status change, and the legal/administrative basis. A record is "active for reporting" only when lifecycle_status == ACTIVE and (for casual/JO/contractual) is_renewed == true for the current period.
1B.2 Live-report exclusion (extends the is_renewed gate): exclude from ALL live statistical reports and any operational report — Executive Dashboard, GAD/analytics, Personnel Inventory, Performance Management/SPMS, and every Module 12 scoreboard — any employee who is not active-for-reporting: i.e., regular/permanent who are separated/retired/terminated, AND casual/JO/contractual who are not renewed. As with Module 1, this is query-level exclusion (WHERE lifecycle_status='ACTIVE' AND is_renewed=true where applicable) — records are NEVER deleted at this stage, only filtered out of live views so statistics reflect the genuinely active workforce. Historical/longitudinal reports may still include past personnel where explicitly requested and permitted, clearly labeled as historical.
1B.3 Archival on separation: when an employee becomes inactive (separation/retirement/termination/end-of-term, or casual/JO/contractual non-renewal that ends the engagement), their record is moved to an ARCHIVED state — retained, secured, removed from live/active rosters and reports, but fully preserved and retrievable by authorized Records staff. Archiving is a status transition, not deletion. 201 files are handled as Confidential/Restricted records per NAP Circular 4. The archived record continues to accrue its retention clock toward eventual disposition.
1B.4 Lawful disposal only (never auto-delete): records are disposed of (destroyed) only after their NAP-approved retention period lapses AND only through the audited disposal workflow — NEVER by an automated hard-delete. Per R.A. 9470 Sec. 18 Art. III, no public record may be disposed of or destroyed except with the prior written authority of the NAP Executive Director. The system computes when a record becomes ELIGIBLE for disposal (retention elapsed), routes it to the Disposal View (NAP Form No. 1 inventory layout, Module 2.3), and keeps the hard-delete locked until the signed NAP Form No. 3 (Authority to Dispose) is uploaded and verified. Permanent records (e.g., appointments CS Form 33-A/B, core 201 assets) are NEVER eligible for disposal — retained indefinitely. The system marks records as Temporary (with a retention period) or Permanent per the matrix in 1B.5.
1B.5 PORTABLE RECORDS RETENTION & DISPOSAL MATRIX (configurable online reference): build a Records-module setting/screen — a portable, user-friendly matrix that lets users look up, for any record series, its full lifecycle: how long it stays active in office, how long in storage/archive, and its final disposition (permanent preservation or destruction). Implement as a configurable table tbl_retention_schedule (series_id, record_series_title, description, record_category e.g. 201/Leave/Appointment/Disciplinary/Financial/LGU, time_value ENUM('PERMANENT','TEMPORARY'), active_period, storage_period, total_retention, disposition_action ENUM('PERMANENT_PRESERVATION','DESTRUCTION','REVIEW'), legal_basis, nap_grds_item_ref, remarks, last_updated). Seed it from the current NAP General Records Disposition Schedule (the 2023/2024 updated GRDS under NAP General Circular No. 5) and the agency's own Records Disposition Schedule (NAP Form No. 2), and make it editable by the Records Officer so it stays current as NAP issues updates. The matrix is the single online reference that drives the retention clock for every document/record (the IDCC Stage 8 retention_class maps to a series in this matrix — single source, no divergence). Display it as a searchable/filterable, exportable reference (search by series, category, disposition; export to PDF/CSV matching NAP Form No. 2 layout). Each employee/document view can show its applicable retention row inline ("This record series: 201 File — Confidential — retention per [legal basis] — disposition: [action] — eligible for disposal on [computed date]") so any user can see, at a glance, where a record is in its lifecycle and when it may be disposed.
1B.6 Lifecycle/retention dashboard (Records canonical scoreboard, per Module 12): the Records/IDCC scoreboard (canonical owner of document/retention stats) shows counts by lifecycle state (active/archived/eligible-for-disposal/pending NAP authority/disposed), records approaching retention end (advance warning so the Records Officer can prepare NAP Form No. 3), and disposal actions completed — aggregate only, RACCS items as anonymized counts, respecting RBAC. No new duplicate board; this extends the existing IDCC/Records owner row in the Metric Ownership Registry (12.8).
1B.7 RBAC & audit: lifecycle status changes (separation/archival) and any disposal action are gated to authorized Records/HRMO roles (lifecycle_manage, disposal_approve bits in Module 4A) and fully audit-logged. The retention matrix is editable only by the Records Officer role. Archived/separated personnel records, especially 201 and disciplinary, retain their confidentiality and RACCS gating after archival. Disposal eligibility is computed and SURFACED automatically, but execution always requires the human-authorized, NAP-cleared workflow.
1B.8 Compliance citations (embed in the matrix, disposal view, and tooltips): R.A. 9470 (NAP Act of 2007) Sec. 18 Art. III (no disposal without NAP Executive Director authority); NAP General Records Disposition Schedule (current 2023/2024 GRDS under NAP General Circular No. 5); NAP Form No. 1 (Records Inventory), NAP Form No. 2 (Records Disposition Schedule), NAP Form No. 3 (Authority to Dispose); NAP Circular 4 (201 files = Confidential/Restricted); R.A. 10173 (privacy of separated-employee personal data — retained securely, disposed lawfully).

MODULE 2B — LEAVE VIOLATION MONITORING, NOTICE GENERATION & PAYROLL COORDINATION
Additive to the Leave module (M2) and the IDCC/Records pipeline. Captures each employee's current leave balances and attendance status, detects violations related to leave administration (leave without pay, absence without pay, AWOL, undertime, tardiness, and related infractions), generates a dynamic watchlist/report of employees to be issued or already issued notices, generates the correct legally-grounded letter per violation type, auto-records any issued notice into the employee's record, and generates coordination letters to affected offices (e.g., Accounting/Payroll) for dropping from payroll or salary deduction. JO/COS are excluded from civil-service leave workflows per the cross-cutting guardrail and are not subject to leave-credit violations (their engagements are governed by their contracts, not the Omnibus Rules on Leave).
2B.1 Data capture: read current VL/SL balances from tbl_leave_ledger; read attendance/DTR data (tardiness minutes, undertime, absences, LWOP days) for the rating period. Compute per employee: VL balance, SL balance, total tardiness instances per month, total undertime, count of unauthorized/LWOP absence days, and consecutive-absence streak. Tardiness and undertime are deducted from VACATION leave credits only, never sick leave, unless the undertime is for health reasons supported by a medical certificate and leave application (Omnibus Rules on Leave, CSC MC No. 41 s.1998, Sec. 34). Offsetting tardiness/absences by working beyond regular hours is NOT allowed (per CSC enhanced work-hours guidelines); the engine must not net these out.
2B.2 Violation detection thresholds (current law — make thresholds configurable in an admin table but seed with these defaults and cite them):
- HABITUAL TARDINESS (light offense, 2025 RACCS Rule 10 §63(C)(10)): tardiness, regardless of minutes, ten (10) times a month for at least two (2) months in a semester OR at least two (2) consecutive months during the year. Penalty ladder: reprimand (1st), 1–30 days suspension (2nd), dismissal (3rd).
- HABITUAL ABSENTEEISM (grave offense, 2025 RACCS): unauthorized absences exceeding the allowable 2.5 days monthly leave credit for at least three (3) months in a semester OR three (3) consecutive months in a year. Penalty: suspension 6 months 1 day to 1 year (1st), dismissal (2nd).
- AWOL (Omnibus Rules on Leave Sec. 63): continuously absent without approved leave for at least thirty (30) calendar days → separated/dropped from the rolls without prior notice; if less than 30 days, a written Return-to-Work Order is served to the last known address, and failure to return within the stated period is a valid ground to drop from the rolls. Also flag the circumvention pattern (substantial absences though less than 30 days, repeated such that a pattern is apparent).
- LWOP / ABSENCE WITHOUT PAY: flag when VL/SL credits are exhausted and further absence/undertime/tardiness converts to leave/absence without pay; track LWOP day totals for payroll coordination and for the Sec. 62 one-year-LWOP automatic-separation watch.
- UNDERTIME / TARDINESS DEDUCTION TRACKING: continuously deduct from VL; when VL is exhausted, subsequent undertime/tardiness becomes without pay and is flagged for payroll deduction.
The engine classifies each flagged employee by violation type and current offense count (1st/2nd/3rd) read from prior recorded notices, so the correct penalty tier and letter are selected.
2B.3 Dynamic violation report/watchlist: a live, filterable report listing employees with detected or pending violations, grouped by violation type and by office/unit, showing: name, office, current VL/SL balance, the specific violation, the counts driving it (e.g., tardiness instances per month across the qualifying months), offense number, current status (Detected / Notice Pending / Notice Issued / Responded / Resolved / Escalated), and the recommended action. Filters: by office, violation type, offense tier, rating period, status. Sort by severity. Export to CSV/PDF with the standard header/footer and legal citations. This report is the issuance worklist for HRMO.
2B.4 Letter generation (per violation, current law): generate the correct letter template based on violation type and offense tier. Distinct templates at minimum: (a) Return-to-Work Order (AWOL < 30 days, Omnibus Rules Sec. 63); (b) Notice of Habitual Tardiness with the applicable penalty tier (2025 RACCS Rule 10 §63(C)(10)); (c) Notice of Habitual Absenteeism (grave offense, 2025 RACCS); (d) Notice/advice on LWOP and its consequences including the Sec. 62 one-year automatic-separation rule; (e) Show-Cause / notice to explain where due process requires the employee to respond before penalty. Each letter must: cite the specific current legal basis and section; state the documented facts (dates, counts, balances) pulled from the data; observe due-process language (opportunity to explain where required before any penalty is imposed); include signature blocks per the office's signature hierarchy; and carry the office letterhead. Letters are drafts for HRMO review and signature — the system generates and routes them, it does not by itself impose penalties. Penalties for grave offenses require the formal administrative process under 2025 RACCS; the system's letters initiate/serve notice, not adjudicate.
2B.5 Auto-recording into the employee record: when a notice/letter is officially issued (marked Issued by an authorized user), the system writes the issuance into the employee's record through the IDCC/Records pipeline — creating a tbl_doc_metadata entry (doc_type e.g. LEAVE-VIOL-NOTICE), linking it to the personnel_id, attaching the generated letter PDF, recording issuance date, violation type, offense tier, and issuing officer, and writing an audit-log row. This builds the documented offense history that drives future offense-tier counting. Records of disciplinary notices follow retention rules (permanent if resulting in major penalty/dismissal, otherwise long-term cap) per Module 9 Stage 8.
2B.6 Office/payroll coordination letters: generate coordination letters to the office that needs to act or be informed. At minimum: (a) a letter to the Accounting/Payroll Office to DROP the employee from the payroll (for AWOL/dropped-from-rolls/separation cases) citing the legal basis and effective date; (b) a letter to Accounting/Payroll FOR INFORMATION on salary deduction (for LWOP days, undertime/tardiness that became without pay after VL exhaustion) with the computed days/amounts to deduct; (c) a letter informing the employee's home office/Department Head of the action. Each coordination letter pulls the computed figures (LWOP days, deduction basis, effectivity), carries proper letterhead and signature hierarchy, and on official issuance is recorded via IDCC and audit-logged. Do not transmit payroll actions silently — they are formal letters routed for signature, then recorded.
2B.7 Due process & safeguards: the system must support the civil-service due-process sequence — for offenses requiring it, a show-cause/notice-to-explain precedes any penalty recommendation; the report status flow (Detected → Notice Pending → Issued → Responded → Resolved/Escalated) enforces that an employee response window is captured before escalation. The system flags but does not auto-impose grave-offense penalties; those route to the formal 2025 RACCS administrative process (and, where confidential, into the RACCS wall, Module 9 Stage 5 / Module 10 M3). All thresholds, penalty tiers, and letter templates are admin-configurable so they can be updated when CSC issuances change, but ship seeded with the current law cited in 2B.2.
2B.8 RBAC: visible under a Leave Violation sub-module in the RBAC matrix (Module 4A). Detection/report viewing for HRMO Leave Administration staff; letter generation and issuance gated to authorized HRMO officers; payroll coordination issuance gated appropriately; only authorized roles may mark a notice Issued (which triggers auto-recording). Every detection-to-issuance action is audit-logged.
2B.9 Compliance citations (embed in report footers, letters, and tooltips): Omnibus Rules on Leave (CSC MC No. 41 s.1998) Sec. 34 (tardiness/undertime vs VL), Sec. 62 (one-year LWOP automatic separation), Sec. 63 (AWOL/Return-to-Work Order/30-day rule); 2025 RACCS Rule 10 §63 (habitual tardiness light offense; habitual absenteeism grave offense; penalty ladders); CSC enhanced government work-hours guidelines (no offsetting); R.A. 6713 (Code of Conduct). 2B.10 LEAVE-FILING PROCEDURE VIOLATIONS (late/improper filing): in addition to attendance violations, the engine detects violations of the leave APPLICATION/FILING rules and generates the corresponding letter with current citations. Detect and classify, per the Omnibus Rules on Leave (CSC MC No. 41 s.1998) and current CSC issuances:
- LATE FILING OF SICK LEAVE (Sec. 53): sick-leave application not filed immediately upon the employee's return from leave; flag when filing date exceeds the prescribed/return window. Sick leave in excess of five (5) successive days lacking the required medical certificate is a separate deficiency flag; where medical consultation was not availed, an affidavit is required in lieu — flag if neither is attached.
- LATE/IMPROPER FILING OF VACATION LEAVE (Sec. 51): VL not submitted five (5) days in advance of the effective date (whenever possible); flag advance-notice violations distinguishing genuinely unforeseeable cases.
- LATE FILING OF SPECIAL PRIVILEGE LEAVE / SLB / other leave types: filed outside the prescribed prior-filing window (e.g., SPL at least one week prior except emergencies); flag per the specific leave type's rule.
- MISSING/DEFICIENT SUPPORTING DOCUMENTS: required medical certificate, proof, or affidavit not attached for the leave type/duration that requires it.
- UNFILED ABSENCE / FAILURE TO FILE: absence incurred with no leave application filed at all within the prescribed period.
Consequence logic: failure to file within the prescribed period may cause DISAPPROVAL of the application (current CSC rule). A disapproved or unfiled leave converts the absence to UNAUTHORIZED — without pay, and counting toward habitual absenteeism / AWOL tracking in 2B.2. The engine links a filing violation to its downstream effect (disapproval recommendation, conversion to LWOP, escalation to attendance-violation tracking) so the two are consistent and not double-counted.
2B.11 FILING-VIOLATION LETTERS & ACTIONS: generate the correct letter per filing violation, each citing the specific current section: (a) Notice of Late/Improper Filing of Leave (citing Sec. 53 for sick leave, Sec. 51 for vacation leave, or the relevant leave-type rule) stating the facts (leave type, dates, filing date vs prescribed period) and the consequence; (b) Notice of Disapproval of Leave Application with the legal ground and the resulting status (absence rendered unauthorized/without pay) and the employee's remedy/period to respond; (c) Notice to Submit Lacking Requirement (medical certificate/affidavit) with the deadline; (d) where a pattern of late/improper filing forms part of habitual absenteeism or warrants disciplinary action, route to the show-cause/notice-to-explain flow (2B.4) and, for grave matters, to the formal 2025 RACCS process. Letters observe due process (opportunity to explain before adverse action where required), carry letterhead and signature hierarchy, and on official issuance auto-record to the employee's record via IDCC and audit-log (2B.5). These letters and their statuses flow through the same Detected→Notice Pending→Issued→Responded→Resolved/Escalated lifecycle and the same Leave-Violation RBAC and scoreboard as attendance violations — filing violations appear as their own category in the watchlist and the 2B scoreboard, without duplicating the attendance counts. Thresholds, windows, and templates are admin-configurable, seeded with the current law. Add to 2B.9 citations: Omnibus Rules on Leave Sec. 51 (vacation leave filing 5 days in advance), Sec. 53 (sick leave filing immediately upon return; medical certificate beyond 5 days), Sec. 54/56, and the current CSC rule that failure to file within the prescribed period may cause disapproval; CSC MC No. 41 s.1998 as amended (incl. CSC MC No. 05 s.2021 / CS Form No. 6 revised).

MODULE 3A — INCIDENT REPORT RECORDING WITH AI-ASSISTED CITATION & COUNSELING SUPPORT
Additive. Captures incident reports, provides an AI/rules-ASSISTED advisory draft of applicable violation citation, possible penalty range, and recommended counseling/improvement action, then routes for human review. CORE SAFEGUARD: the AI/rules output is an ADVISORY DRAFT ONLY, clearly labeled as such, never a determination or finding. A designated officer (per RBAC) reviews, edits, and owns every output. The system assists; it never adjudicates. This protects due process under the 2025 RACCS and avoids COA/appeal exposure from automated disciplinary action.
3A.1 Incident capture (basic information): a structured intake form recording — incident reference number (auto), date/time of incident, date reported, location, reporting party (name/role), person(s) involved (link to personnel_id where applicable), witnesses, incident category (e.g., attendance-related, conduct, performance, safety, property, interpersonal, other), a free-text factual narrative (what happened, observable facts only), immediate action taken, and attachments (photos, documents, statements) ingested through the IDCC pipeline. Capture facts, not conclusions; the narrative field prompts for observable facts and avoids pre-judging intent.
3A.2 AI/rules-assisted advisory draft: on submission of the facts, an assist engine produces a clearly-labeled ADVISORY DRAFT containing: (a) suggested applicable provision(s) — candidate citations from the 2025 RACCS (and related issuances) that the described facts may fall under, each shown with the rule/section and offense classification (light/less grave/grave) and a confidence/relevance note; (b) possible penalty RANGE for each candidate provision and offense tier (e.g., reprimand → suspension → dismissal ladders), pulled from the rules table, presented as a range not a verdict; (c) recommended counseling/improvement action — constructive, developmental suggestions (e.g., coaching session, performance improvement plan, expectation-setting, referral to employee wellness) aimed at correction and improvement rather than punishment. Implementation of the assist engine (on-premise local model vs deterministic rules-based mapping of facts→provisions; no external API for SPI) is decided in Phase A; either is acceptable provided no SPI leaves the LAN. Every draft is watermarked/labeled: "ADVISORY DRAFT — AI/RULES-ASSISTED. NOT A FINDING OR PENALTY. For review and determination by the authorized officer under 2025 RACCS due process."
3A.3 Mandatory human review & ownership: the advisory draft routes to the authorized reviewing officer (per RBAC) who must review, may edit any citation/penalty/recommendation, and must explicitly accept or override before anything is finalized. The system records the officer's edits and final decision, the original AI/rules draft, and the delta between them (so it is auditable what the human changed). Nothing is recorded as an official action until a human finalizes. The reviewing officer's identity, decision, and timestamp are stored and audit-logged.
3A.4 Dual track — counseling vs RACCS escalation: classify each finalized incident as either (a) LIGHT/DEVELOPMENTAL — stays in this module as a counseling/coaching record with the recommended improvement action, a counseling-session log (date, attendees, agreed actions, follow-up date), and a non-punitive tone; or (b) GRAVE/FORMAL — escalates into the formal disciplinary process and, where confidential, into the RACCS Confidentiality Wall (Module 9 Stage 5 / Module 10 M3) with all its air-gap, MFA, and access-logging protections. The reviewing officer (not the AI) sets the track; the system may suggest the track based on the candidate offense classification but the human confirms. Counseling-track records carry a lighter retention and are NOT treated as administrative penalties; escalated records follow RACCS handling and retention.
3A.5 Counseling & improvement support (developmental focus): for the counseling track, provide a structured counseling record: the constructive recommendation, an agreed improvement/action plan with target dates, a session log, and follow-up scheduling with reminders to the supervisor/HRMO. The emphasis is correction, support, and improvement (consistent with employee-wellbeing and progressive-discipline principles), not punishment. Where appropriate, surface referral options (wellness, training). This track aims to resolve issues before they become formal cases.
3A.6 Recording & audit: a finalized incident is recorded via the IDCC/Records pipeline (tbl_doc_metadata, doc_type e.g. INCIDENT-REPORT or INCIDENT-COUNSELING / INCIDENT-ESCALATED), linked to involved personnel_id(s) with strict privacy handling — incident records often contain SPI and sensitive content, so apply privacy_tier and, for escalated/confidential matters, the RACCS wall. All access is logged to tbl_audit_log (and tbl_spi_access_log where SPI). Light/counseling records are access-restricted to the involved supervisor, HRMO, and the employee as appropriate; grave/escalated records inherit RACCS access gating.
3A.7 RBAC (configurable): who may CREATE and who may FINALIZE an incident report is fully configurable via the RBAC matrix (Module 4A) — e.g., supervisors create while HRMO finalizes, or HRMO-only, or Department Head + HRMO co-approval, set per the office's policy through permission bits (incident_create, incident_review, incident_finalize, incident_escalate). The AI/rules assist is available to creators/reviewers but only holders of incident_finalize may finalize, and only incident_escalate may push to the RACCS track. Self-reporting and conflict-of-interest: a user cannot finalize an incident in which they are an involved party.
3A.8 Compliance & fairness safeguards: the advisory label is mandatory and non-removable on all AI/rules output; the system never imposes a penalty; due-process sequencing (notice, opportunity to be heard) is preserved for any escalation; the employee's right to respond is captured; the AI draft, human edits, and final decision are all retained for auditability and appeal. Tooltips cite 2025 RACCS (offense classifications and due process), R.A. 6713 (Code of Conduct), and R.A. 10173 (handling of sensitive incident data). Note that AI/rules suggestions are decision-support only and carry no legal authority; the authorized officer's determination under the 2025 RACCS governs.

Standalone intranet Flask Blueprint (/idcc), on-premise, no external API calls. 8 stages:

2 OCR: on-premise Tesseract; text → LONGTEXT with MySQL FULLTEXT index; low ocr_confidence → flag for human validation.
3 Classification: doc_type_code (APPT-33A, PDS-212, LEAVE-CSC6, DISC-RACCS, LGU-EO, COE-REQ…); importance_class (Vital/Important/Useful/Routine); privacy_tier (1 Restricted/2 Protected/3 Internal); abstract_description (2–3 sentences).
4 Data-Privacy Triage (R.A. 10173 + NPC): regex/keyword-detect SPI (GSIS BP, PhilHealth, TIN, SSS, addresses, SALN/financial, medical, blood type); on match AES-256 encrypt at rest, set privacy_tier=1, build masked redacted version for standard users; full files restricted; every access → tbl_spi_access_log.
5 RACCS Confidentiality Wall (CSC Res. 2500357): DISC-RACCS docs isolated to an air-gapped directory; EXCLUDED from the global FULLTEXT index, mapped to a separate access-gated index; AES-256 at rest; MFA restricted to Disciplining Authority/Legal Officers/active CODI; all attempts logged to an air-gapped security log.
6 Relationship Mapping: tbl_doc_relations (e.g., Transcript SUPPORTING_ELIGIBILITY to an appointment; medical cert to a CSC Form 6); link via names/indexes to personnel_id.
7 Auto-Foldering: partition by doc_type_code + privacy_tier + importance_class; confidential/SPI inherit Stage 4–5 restrictions; standard users cannot hard-delete.
8 Retention (R.A. 9470 + NAP RDS): Appointments (33-A/B) & core 201 = Permanent; PDS (212) = active tenure then post-separation review; disciplinary = permanent if dismissal/major penalty else long-term cap; CSC Form 6 leave = per accounting/audit, disposal only after a verified consolidated ledger, always audited.

MODULE 9A — MULTI-SOURCE DOCUMENT CAPTURE & VISION ENRICHMENT (IDCC FRONT DOOR)
Additive enhancement to IDCC Stage 1 (Ingestion) and Stage 2 (OCR). Upgrades the document front door for EVERY attachment field in the system (applicant letters, employee 201 records, photos, training certificates, leave documents, incident attachments, LGU documents, etc.) from simple upload to a universal multi-source capture + intelligent extraction layer. CRITICAL: this is the front door TO the IDCC pipeline, never a bypass — every captured payload, regardless of source, enters at IDCC Stage 1, receives its SHA-256 hash, and flows through privacy triage (Stage 4) and the RACCS wall (Stage 5) exactly like an uploaded file. Capture method is recorded as an attribute (capture_source: UPLOAD | WEBCAM | SMARTPHONE | BLUETOOTH | SCANNER), never a reason to skip any stage.
9A.1 Hardware ingestion layer (all three prioritized equally): (a) WEBCAM / SMARTPHONE CAMERA — in-browser capture via WebRTC getUserMedia / native device camera APIs; live preview, snapshot, multi-shot for multi-page docs; mobile-friendly (the LAN app opened on a phone can capture directly). (b) SCANNER / ATTACHED PRINTER — TWAIN/WIA integration via a small client-side bridge (a local helper service, since browsers cannot speak TWAIN directly) that triggers the scan and pushes the payload to the backend; supports flatbed and ADF (multi-page) for bulk 201-file digitization. (c) BLUETOOTH — a listener/receiver service accepting files/images transferred from mobile devices (Web Bluetooth where supported, or a paired OBEX/RFCOMM receiver on the host). Bluetooth is SECURITY-GATED: disabled by default, enabled only via RBAC by an Administrator, paired-device allowlist, and flagged in Phase A for security review (open Bluetooth receivers are an attack surface on a network holding personnel data). All three sources deposit into the same ingestion intake; the rest of the pipeline is source-agnostic.
9A.2 Supported formats & content: PDF, JPEG, PNG, TIFF, and raw image payloads; handle high-resolution clean scans, skewed/low-light mobile photos of physical documents, and variable handwritten notes. Multi-page (PDF, multi-shot, ADF) is assembled into a single document record where appropriate.
9A.3 Pre-processing (before OCR, on-premise): automated image normalization, deskew, contrast/brightness adjustment, denoise, and edge-detection auto-crop to isolate the document from background — optimizing the payload for extraction. Low-quality captures get a quality score; below threshold prompts recapture or flags for human validation (ties into existing Stage 2 ocr_confidence handling). Implemented with on-premise libraries (e.g., OpenCV); no external calls in pre-processing.
9A.4 TIERED EXTRACTION (privacy-bound — this is the core safeguard): extraction tier is chosen by sensitivity, never "everything to a Vision LLM":
- TIER 1 PRINTED TEXT → on-premise Tesseract (existing Stage 2). Default for clean printed documents. No data leaves the LAN.
- TIER 2 HANDWRITING / MESSY PHOTOS → an ON-PREMISE vision/handwriting model hosted on the LAN (e.g., PaddleOCR handwriting models, TrOCR, or a self-hosted open vision-language model). Handles handwritten notes and unstructured photos. No data leaves the LAN.
- TIER 3 EXTERNAL VISION LLM (e.g., GPT-4o / Claude) → PERMITTED ONLY for documents that are explicitly NON-SPI and NON-RACCS, AND only after the document passes an automated privacy pre-check (the Stage 4 SPI regex/keyword triage runs FIRST; any SPI match blocks the external tier), AND only when an Administrator has explicitly opted in to external processing via RBAC. Default = OFF. The privacy pre-check, the opt-in state, and every external call (what doc class, when, by whom) are audit-logged. If any SPI is detected or the opt-in is off, the system falls back to Tier 1/2 on-premise. No SPI or RACCS content ever reaches an external API. (This realizes the chosen policy: on-premise default, external allowed only for explicitly non-SPI docs after privacy pre-check + admin opt-in.)
9A.5 Pipeline continuity: extracted text (any tier) commits to the existing Stage 2 LONGTEXT + FULLTEXT index, then continues through Stages 3–8 (classification, privacy triage, RACCS wall, relationship mapping, auto-foldering, retention) unchanged. RACCS-classified documents NEVER use Tier 3 regardless of opt-in. The capture_source and extraction_tier are stored on the document record for audit.
9A.6 Universal attachment integration: any attachment field across the system (applicant letter, 201 record, photo, training certificate, leave/medical document, incident attachment, LGU document) can invoke the capture widget — "Upload / Capture" — offering file upload, webcam/phone snapshot, scanner, or (if enabled) Bluetooth, all landing in IDCC. The existing photo-management 201 routine (Module 7) and the application_letter_attachment gate (Module 4) reuse this capture layer rather than implementing their own. This single front door means improving capture improves every attachment in the system at once.
9A.7 RBAC & audit: capture is RBAC-gated (a capture_use bit; bluetooth_capture and external_vision_optin as separate sensitive bits held by Administrators). Every capture records source, user, timestamp, and resulting doc_id to the audit log. Bluetooth and external-Vision bits are flagged sensitive in the RBAC matrix (Module 4A) and surfaced on the RBAC scoreboard.
9A.8 Implementation strategy (deliver in this sequence): STEP 1 — architecture & tech stack: data flow from hardware layer (WebRTC for webcam/phone; a TWAIN/WIA client bridge for scanners; Web Bluetooth/OBEX receiver for Bluetooth) to the backend intake, with recommended on-premise libraries (OpenCV pre-processing; Tesseract Tier 1; PaddleOCR/TrOCR or self-hosted VLM Tier 2). STEP 2 — core processing pipeline: a modular prototype showing an image payload pre-processed (normalize/deskew/crop) then routed to the correct extraction tier (privacy pre-check gating Tier 3) and converted to structured text that enters IDCC Stage 2. STEP 3 — scanner microservice first: the focused backend microservice/endpoint that listens for the local TWAIN/WIA scanner payload (via the client bridge), validates the file, and pushes it into the Step 2 pipeline — prioritized first as the highest-value, lowest-risk, fully-local capture path for bulk 201 digitization. Webcam/phone and Bluetooth capture follow, built to the same intake contract.
9A.9 Compliance: on-premise default keeps SPI within the LAN per R.A. 10173 and NPC Circular 16-01; the external tier is a narrow, audited, opt-in exception for non-sensitive documents only; Bluetooth is security-gated; all capture flows through IDCC privacy triage and the RACCS wall. Tooltips cite R.A. 10173 and NPC Circular 16-01 on the capture and external-Vision-opt-in controls. Capture statistics (by source, tier, volume) register to IDCC/Records as their canonical scoreboard owner (Module 12.8), not a new duplicate board.

9A.10 DUPLICATE-ATTACHMENT DETECTION & RESOLUTION: prevent silent duplication of the same file across attachment fields and records, using the SHA-256 hash already computed at IDCC Stage 1 (tbl_doc_metadata.sha256_hash is UNIQUE). On every capture/upload/attach, BEFORE committing, the system checks the new file's hash against existing document records.
- EXACT DUPLICATE (identical hash): if the same file already exists, do NOT silently reject or silently create a second copy. Notify the user clearly: "This file has already been uploaded." Show WHERE the existing copy is attached — its location(s): the record/employee, the module, the field, the date ingested, and who ingested it (subject to the viewer's RBAC scope; if the existing copy sits on a record the user may not see, say so generically without leaking restricted detail). Provide a link to the existing location where permitted.
- RESOLUTION OPTIONS: offer the user clear choices — (a) USE EXISTING / LINK: attach a reference to the already-stored document to this field instead of storing a second copy (preferred — preserves the single-source, no-duplicate principle and saves storage); (b) OVERWRITE: replace the existing file with the new one (only where the user has Edit rights on the target; overwrite is a soft-replace — the prior version is retained per retention/audit rules, never hard-deleted, consistent with the no-unguarded-delete rule); (c) KEEP BOTH / attach anyway with a reason: only if a legitimate distinct need exists, requiring a short justification recorded on the record (discouraged; the system notes it as an intentional duplicate).
- INDIVIDUAL vs COLLECTIVE RESOLUTION: when a batch/multi-file capture (multi-shot, ADF scan, batch import, or multiple drag-drop) contains one or more duplicates, present a batch resolution screen listing each detected duplicate with its existing location, and let the user resolve them INDIVIDUALLY (decide per file) OR COLLECTIVELY (apply one choice — Use Existing / Overwrite / Keep Both — to all detected duplicates at once), with a per-row override. Non-duplicate files in the batch proceed normally.
- NEAR-DUPLICATE (optional, advisory): where feasible, flag likely near-duplicates (same document re-scanned/re-photographed so the hash differs but content matches — e.g., via perceptual/image hash or OCR-text similarity) as a softer "This looks similar to an existing document at [location] — is it the same?" advisory, never an auto-block; the user confirms. This catches the common case of the same physical document scanned twice.
- INTEGRITY & AUDIT: overwrites and intentional keep-both choices are audit-logged (who, when, which existing doc, chosen action, justification). Duplicate detection respects RBAC (never reveal the existence or location of a document on a record the user cannot access — in that case show only "an identical file exists on a record you are not authorized to view; contact HR Records"). RACCS/confidential documents are never surfaced as dedup hints to unauthorized users. Deduplication reinforces the single-source principle already used for metrics and training hours: one canonical stored document, referenced from many places, rather than many copies that can diverge.
- UX: the duplicate notice is clear and non-punitive ("Looks like this is already on file") with the existing location and the resolution options inline; collective controls are obvious for batches; the default highlighted option is USE EXISTING / LINK to steer toward no duplication.

MODULE 12 — DYNAMIC STATISTICAL SCOREBOARD (SYSTEM-WIDE, EQUITABLE, NON-REDUNDANT)
A single, consistent, living statistical layer across the ENTIRE system — every module and sub-module — built from one shared, reusable scoreboard component. The design is equitable (each module gets the depth of statistics it actually warrants — no more, no less), non-redundant (each metric has exactly one canonical home; the same number is never counted/displayed in two places), and built to be friendly, informative, and visually alive. CORE CONSTRAINT (unchanged): every scoreboard respects its host module's privacy, RBAC, confidentiality, and is_renewed gating — aggregate only; never SPI, never RACCS/confidential content, never pre-comparison deliberation scores, never incident names/narrative.
12.1 ONE SHARED COMPONENT: build a single reusable scoreboard widget used everywhere — KPI stat tiles (large number, label, trend arrow, sparkline), charts (bar/line/donut/progress via the existing library), a filter bar matching the host module's filters, live auto-refresh (10–15s polling or existing real-time channel; manual refresh + "last updated" stamp), and export (CSV/PDF, standard header/footer + citations, logged). Themed entirely via theme.css semantic variables. Every scoreboard in the system is an instance of THIS component — never bespoke one-offs — so look, behavior, and accessibility are uniform.
12.2 EQUITABLE ALLOCATION (right-sized per module, not uniform): scale the scoreboard to each module's actual decision value. Three tiers: (a) FULL scoreboard (KPI row + 2–4 charts + trends) for analytics-heavy modules — GAD/Workforce, Leave Violations, Incidents, Renewal, IDCC/Records, Executive Dashboard; (b) COMPACT scoreboard (a slim KPI strip, 2–4 tiles, optional one mini-chart) for operational modules where stats inform but aren't the point — Recruitment view, Plantilla, LGU service requests, Photo/intake; (c) INLINE metric (a single contextual figure or progress indicator, no full board) for narrow sub-modules — e.g., a vacancy's applicant-count badge, a member's completion fraction. A module gets a FULL board only if it has decisions that statistics meaningfully drive; otherwise compact or inline. This prevents dashboard bloat and keeps each view purposeful.
12.3 NON-REDUNDANCY — CANONICAL OWNERSHIP OF EACH METRIC: every statistic has ONE canonical home module that owns and displays it in full; other modules that need the same figure show it only as a lightweight contextual reference (a single tile or a linked figure), never a re-computed duplicate board. Establish a shared metrics service so all surfaces read the same computed value from one source (no parallel counts that can disagree). Canonical owners (examples): active/not-renewed headcount → Renewal (1A); workforce demographics (sex/PWD/solo-parent/age/SG) → GAD/Workforce; leave-violation counts/funnel → Leave Violations (2B); incident counts/tracks → Incidents (3A); deliberation completion → Monitoring Board (6A); document/retention stats → IDCC/Records; sensitive-bit holders → RBAC (4A, Admin). If module B needs module A's number, it shows a small "reference tile" that links to A's full board — it does not rebuild the chart. The Executive Dashboard is the ONLY place that aggregates across owners, and it pulls each headline figure from its canonical owner (one source of truth), presenting a curated cross-system summary rather than re-counting.
12.4 FRIENDLY, INFORMATIVE, APPEALING, ACTIVE (the display standard for every instance):
- Clarity first: each tile states what the number means in plain language and its timeframe; avoid jargon; every chart has a one-line plain-language takeaway (auto-generated insight caption) so a non-analyst instantly understands "what this is telling me."
- Active/alive: smooth count-up animation on load, live updating values, animated trend arrows (up/down/flat) with color from semantic theme variables, sparklines showing recent movement, and subtle transitions on refresh (never jarring). A gentle "updated just now" pulse on the last-updated stamp.
- Informative depth on demand: tiles are calm by default but expandable — click/tap to reveal the breakdown, the trend over periods, and the contributing factors (progressive disclosure keeps the surface uncluttered while depth is one tap away).
- Appealing & purposeful: generous whitespace, clear visual hierarchy (one hero metric per board, supporting metrics secondary), consistent iconography, semantic color used meaningfully (success/warning/danger conveys state, not decoration), and empty/zero states that are encouraging and clear ("No violations this period — all clear") rather than blank.
- Actionable: where a statistic implies an action, surface a contextual link ("3 notices pending → review") so the board drives work, not just observation — but only within the user's RBAC scope.
- Accessible & responsive: WCAG 2.1 AA contrast (theme themes already validated), keyboard-navigable, screen-reader labels on every figure and chart, and graceful reflow — KPI tiles stack and charts simplify on mobile; never a cramped grid on small screens.
12.5 PRIVACY/RBAC/GATING (unchanged, applies to every instance): RBAC-scoped (counts reflect only permitted data; supervisors see only their unit); privacy-first (aggregate only — no SPI, no confidential/RACCS content, no pre-comparison deliberation scores, no incident names/narrative; escalated/grave and RACCS items appear only as anonymized counts); is_renewed-gated where the metric concerns active personnel; exports logged; tooltips carry the host module's legal citations. The privacy and aggregation rules are enforced IN the shared component, so no instance can bypass them.
12.6 INTELLIGENT, NOT NOISY: scoreboards surface what changed and what needs attention rather than dumping every possible count. Prioritize: deltas (what moved since last period), exceptions (what crosses a threshold), and readiness/completion (what is/ isn't done). Suppress static, low-value counts. The goal is a board a busy HRMO chief can read in ten seconds and know what needs action — informative density without clutter.

12.7 EXISTING-DISPLAY AUDIT & CONSOLIDATION (Phase A/B/C, before any build): conforming to this module means rationalizing displays that already exist — not a blind sweep. During the discovery protocol the developer MUST: (a) Phase A — inventory EVERY existing statistical display, KPI tile, chart, and count across the current system, recording for each its location, the metric(s) shown, and how each is computed; (b) Phase B — identify redundancy (the same figure displayed or re-counted in more than one place) and map each metric to its single proposed canonical owner per 12.3 and the registry in 12.8; (c) Phase C — present a written DE-DUPLICATION / CONSOLIDATION MAP for approval: for each duplicated metric, the proposed canonical owner, which displays collapse into reference tiles, which boards downgrade from FULL to COMPACT or INLINE per 12.2, and which bespoke displays are replaced by the shared component; then STOP for approval. Only after approval, execute the consolidation, preserving every working feature. Treat existing boards as something to audit and rationalize, never to ignore or silently delete.
