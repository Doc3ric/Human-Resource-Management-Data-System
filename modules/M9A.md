MODULE 9A — MULTI-SOURCE DOCUMENT CAPTURE & VISION ENRICHMENT (IDCC FRONT DOOR)
Additive enhancement to IDCC Stage 1 (Ingestion) and Stage 2 (OCR). Upgrades the document front door for EVERY attachment field in the system (applicant letters, employee 201 records, photos, training certificates, leave documents, incident attachments, LGU documents, etc.) from simple upload to a universal multi-source capture + intelligent extraction layer. CRITICAL: this is the front door TO the IDCC pipeline, never a bypass — every captured payload, regardless of source, enters at IDCC Stage 1, receives its SHA-256 hash, and flows through privacy triage (Stage 4) and the RACCS wall (Stage 5) exactly like an uploaded file. Capture method is recorded as an attribute (capture_source: UPLOAD | WEBCAM | SMARTPHONE | BLUETOOTH | SCANNER), never a reason to skip any stage.
9A.1 Hardware ingestion layer (all three prioritized equally): (a) WEBCAM / SMARTPHONE CAMERA — in-browser capture via WebRTC getUserMedia / native device camera APIs; live preview, snapshot, multi-shot for multi-page docs; mobile-friendly (the LAN app opened on a phone can capture directly). (b) SCANNER / ATTACHED PRINTER — TWAIN/WIA integration via a small client-side bridge (a local helper service, since browsers cannot speak TWAIN directly) that triggers the scan and pushes the payload to the backend; supports flatbed and ADF (multi-page) for bulk 201-file digitization. (c) BLUETOOTH — a listener/receiver service accepting files/images transferred from mobile devices (Web Bluetooth where supported, or a paired OBEX/RFCOMM receiver on the host). Bluetooth is SECURITY-GATED: disabled by default, enabled only via RBAC by an Administrator, paired-device allowlist, and flagged in Phase A for security review (open Bluetooth receivers are an attack surface on a network holding personnel data). All three sources deposit into the same ingestion intake; the rest of the pipeline is source-agnostic.
9A.2 Supported formats & content: PDF, JPEG, PNG, TIFF, and raw image payloads; handle high-resolution clean scans, skewed/low-light mobile photos of physical documents, and variable handwritten notes. Multi-page (PDF, multi-shot, ADF) is assembled into a single document record where appropriate.
9A.3 Pre-processing (before OCR, on-premise): automated image normalization, deskew, contrast/brightness adjustment, denoise, and edge-detection auto-crop to isolate the document from background — optimizing the payload for extraction. Low-quality captures get a quality score; below threshold prompts recapture or flags for human validation (ties into existing Stage 2 ocr_confidence handling). Implemented with on-premise libraries (e.g., OpenCV); no external calls in pre-processing.
9A.4 TIERED EXTRACTION (privacy-bound — this is the core safeguard): extraction tier is chosen by sensitivity, never "everything to a Vision LLM":
- TIER 1 PRINTED TEXT → on-premise Tesseract (existing Stage 2). Default for clean printed documents. No data leaves the LAN.
- TIER 2 HANDWRITING / MESSY PHOTOS → an ON-PREMISE vision/handwriting model hosted on the LAN (e.g., PaddleOCR handwriting models, TrOCR, or a self-hosted open vision-language model). Handles handwritten notes and unstructured photos. No data leaves the LAN.
- TIER 3 EXTERNAL VISION LLM (e.g., GPT-4o / Claude) → PERMITTED ONLY for documents that are explicitly NON-SPI and NON-RACCS, AND only after the document passes an automated privacy pre-check (the Stage 4 SPI regex/keyword triage runs FIRST; any SPI match blocks the external tier), AND only when an Administrator has explicitly opted in to external processing via RBAC. Default = OFF. The privacy pre-check, the opt-in state, and every external call (what doc class, when, by whom) are audit-logged. If any SPI is detected or the opt-in is off, the system falls back to Tier 1/2 on-premise. No SPI or RACCS content ever reaches an external API. (This realizes the chosen policy: on-premise default, external allowed only for explicitly non-SPI docs after privacy pre-check + admin opt-in.)
9A.5 Pipeline continuity: extracted text (any tier) commits to the existing Stage 2 LONGTEXT + FULLTEXT index, then continues through Stages 3–8 (classification, privacy triage, RACCS wall, relationship mapping, auto-foldering, retention) unchanged. RACCS-classified documents NEVER use Tier 3 regardless of opt-in. The capture_source and extraction_tier are stored on the document record for audit.
9A.6 Universal attachment integration: any attachment field across the system (applicant letter, 201 record, photo, training certificate, leave/medical document, incident attachment, LGU document) can invoke the capture widget — "Upload / Capture" — offering file upload, webcam/phone snapshot, scanner, or (if enabled) Bluetooth, all landing in IDCC. The existing photo-management 201 routine (Module 7) and the application_letter_attachment gate (Module 4) reuse this capture layer rather than implementing their own. This single front door means improving capture improves every attachment in the system at once.
9A.7 RBAC & audit: capture is RBAC-gated (a capture_use bit; bluetooth_capture and external_vision_optin as separate sensitive bits held by Administrators). Every capture records source, user, timestamp, and resulting doc_id to the audit log. Bluetooth and external-Vision bits are flagged sensitive in the RBAC matrix (Module 4A) and surfaced on the RBAC scoreboard.
9A.8 Implementation strategy (deliver in this sequence): STEP 1 — architecture & tech stack: data flow from hardware layer (WebRTC for webcam/phone; a TWAIN/WIA client bridge for scanners; Web Bluetooth/OBEX receiver for Bluetooth) to the backend intake, with recommended on-premise libraries (OpenCV pre-processing; Tesseract Tier 1; PaddleOCR/TrOCR or self-hosted VLM Tier 2). STEP 2 — core processing pipeline: a modular prototype showing an image payload pre-processed (normalize/deskew/crop) then routed to the correct extraction tier (privacy pre-check gating Tier 3) and converted to structured text that enters IDCC Stage 2. STEP 3 — scanner microservice first: the focused backend microservice/endpoint that listens for the local TWAIN/WIA scanner payload (via the client bridge), validates the file, and pushes it into the Step 2 pipeline — prioritized first as the highest-value, lowest-risk, fully-local capture path for bulk 201 digitization. Webcam/phone and Bluetooth capture follow, built to the same intake contract.
9A.9 Compliance: on-premise default keeps SPI within the LAN per R.A. 10173 and NPC Circular 16-01; the external tier is a narrow, audited, opt-in exception for non-sensitive documents only; Bluetooth is security-gated; all capture flows through IDCC privacy triage and the RACCS wall. Tooltips cite R.A. 10173 and NPC Circular 16-01 on the capture and external-Vision-opt-in controls. Capture statistics (by source, tier, volume) register to IDCC/Records as their canonical scoreboard owner (Module 12.8), not a new duplicate board.

9A.10 DUPLICATE-ATTACHMENT DETECTION & RESOLUTION: prevent silent duplication of the same file across attachment fields and records, using the SHA-256 hash already computed at IDCC Stage 1 (tbl_doc_metadata.sha256_hash is UNIQUE). On every capture/upload/attach, BEFORE committing, the system checks the new file's hash against existing document records.
- EXACT DUPLICATE (identical hash): if the same file already exists, do NOT silently reject or silently create a second copy. Notify the user clearly: "This file has already been uploaded." Show WHERE the existing copy is attached — its location(s): the record/employee, the module, the field, the date ingested, and who ingested it (subject to the viewer's RBAC scope; if the existing copy sits on a record the user may not see, say so generically without leaking restricted detail). Provide a link to the existing location where permitted.
- RESOLUTION OPTIONS: offer the user clear choices — (a) USE EXISTING / LINK: attach a reference to the already-stored document to this field instead of storing a second copy (preferred — preserves the single-source, no-duplicate principle and saves storage); (b) OVERWRITE: replace the existing file with the new one (only where the user has Edit rights on the target; overwrite is a soft-replace — the prior version is retained per retention/audit rules, never hard-deleted, consistent with the no-unguarded-delete rule); (c) KEEP BOTH / attach anyway with a reason: only if a legitimate distinct need exists, requiring a short justification recorded on the record (discouraged; the system notes it as an intentional duplicate).
- INDIVIDUAL vs COLLECTIVE RESOLUTION: when a batch/multi-file capture (multi-shot, ADF scan, batch import, or multiple drag-drop) contains one or more duplicates, present a batch resolution screen listing each detected duplicate with its existing location, and let the user resolve them INDIVIDUALLY (decide per file) OR COLLECTIVELY (apply one choice — Use Existing / Overwrite / Keep Both — to all detected duplicates at once), with a per-row override. Non-duplicate files in the batch proceed normally.
- NEAR-DUPLICATE (optional, advisory): where feasible, flag likely near-duplicates (same document re-scanned/re-photographed so the hash differs but content matches — e.g., via perceptual/image hash or OCR-text similarity) as a softer "This looks similar to an existing document at [location] — is it the same?" advisory, never an auto-block; the user confirms. This catches the common case of the same physical document scanned twice.
- INTEGRITY & AUDIT: overwrites and intentional keep-both choices are audit-logged (who, when, which existing doc, chosen action, justification). Duplicate detection respects RBAC (never reveal the existence or location of a document on a record the user cannot access — in that case show only "an identical file exists on a record you are not authorized to view; contact HR Records"). RACCS/confidential documents are never surfaced as dedup hints to unauthorized users. Deduplication reinforces the single-source principle already used for metrics and training hours: one canonical stored document, referenced from many places, rather than many copies that can diverge.
- UX: the duplicate notice is clear and non-punitive ("Looks like this is already on file") with the existing location and the resolution options inline; collective controls are obvious for batches; the default highlighted option is USE EXISTING / LINK to steer toward no duplication.
